# 자료 저장소(DB) 설계

- 작성일: 2026-10-19
- 대상: 곁 — 이산중학교 사안처리·상담 도우미 (`gyeot`, 이전 폴더 이름 `mindGuide_test`)
- 구현: `store.py`, 저장 파일 `index/gyeot.db`(이전 이름 `mindguide.db`)

## 1. 이전 방식과 문제점

| 항목 | 이전 방식 | 문제 |
|---|---|---|
| 자료 목록 | 기본 4개는 `rag.py` 코드에 고정, 추가 자료는 `data/registry.json` | 목록이 두 곳에 나뉨. 기본 자료는 화면에서 관리 불가 |
| 청크·형태소 | `index/chunks.json` 한 파일(2.5MB) | 자료 하나를 추가·삭제해도 파일 전체를 다시 씀 |
| 임베딩 | `index/embeddings.npy` | `chunks.json`과 **행 순서가 같아야** 함. 둘 중 하나만 바뀌면 검색이 틀어짐(트랜잭션 없음) |
| 주제·층 | 없음 | "주제 DB / 공통 DB / 학교 DB" 구분을 표현할 수 없음 |
| 평가·점검 기록 | `doc_agent/reports/*.json` 파일 | 자료와 연결되지 않음. 이력·알림 관리 불가 |
| 중복 등록 | 파일 이름만 비교 | 같은 PDF를 이름만 바꿔 올리면 막지 못함 |

## 2. 어떤 DB를 쓰나: SQLite (+ 메모리 벡터 검색)

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **SQLite** | 파이썬 기본 포함(설치 없음), 파일 하나, 트랜잭션, 외래키 CASCADE 삭제 | 동시에 여러 명이 쓰는 서버에는 약함, 벡터 검색 기능 없음 | **채택**. 1인 상담사·로컬 실행에 가장 단순하고 안전 |
| Chroma / LanceDB | 벡터 검색·메타데이터 필터 내장 | 새 라이브러리 설치, 다중 주제(목록) 필터가 제한적이거나 버전마다 다름 | 보류 |
| PostgreSQL + pgvector | 다중 사용자, 대용량, SQL + 벡터 검색 | 서버 설치·운영 필요 | **확장 시**(여러 학교·여러 상담사가 같이 쓰는 서비스) |

벡터 검색은 실행할 때 활성 자료의 임베딩을 메모리(numpy)로 읽어 계산합니다. 지금 규모(청크 수백~수천 개)에서는 1초 안쪽입니다. 같은 스키마를 그대로 pgvector로 옮길 수 있게, 임베딩은 청크 행에 함께 저장합니다.

## 3. 세 층(layer)과 주제(topic)

물리적으로 DB를 나누지 않고, **한 저장소에 층·주제 꼬리표를 붙여 필터**합니다. 문서 하나에 주제를 여러 개 붙일 수 있습니다(예: Wee 운영 가이드 = 학교 운영 + 상담 기법 + 정서·위기).

| 층(layer) | 언제 검색하나 | 예시 |
|---|---|---|
| `common` 공통 | 모든 질문(질문 유형만 맞으면) | 법령, 기관 연락처, Wee 운영 가이드 |
| `topic` 주제 | 질문 주제와 자료 주제가 겹칠 때 | 학교폭력 가이드북, 사이버·디지털 상담 매뉴얼 |
| `school` 학교 | 이 학교 질문(학교 맞춤형 등) | 이산중 학생생활규정. 법령·지침보다 하위 |

주제 목록: 학교폭력 / 가정 / 학업·학교부적응 / 정서·위기 / 디지털·사이버 / 상담 기법 / 학교 운영

질문이 들어오면 검색어 생성 호출에서 **질문 유형**(학교 맞춤형·절차·정의·상담·학생 설명·위기)과 **주제**(0~3개)를 함께 판단합니다(추가 API 호출 없음).
- 기본 4개 자료: 질문 유형별 확인 순서(`rag.QTYPES`)대로
- 추가 자료: 그 질문 유형에 쓰도록 등록됐고, 층이 공통·학교이거나 질문 주제와 겹칠 때만 확인 순서 뒤에 붙음. 위기 유형 자료는 위기 질문에서 1순위

## 4. 표 구조

```
schools ─┐
         │ 1:N
documents ──┬─< doc_topics   (문서별 주제, 여러 개)
            ├─< doc_qtypes   (문서를 확인할 질문 유형)
            ├─< chunks       (쪽 단위 청크: 본문·형태소·임베딩)
            ├─< reviews      (입고 평가·정기 점검 기록)
            └─< alerts       (사용 전 알림)  ── reviews(어느 점검에서 나왔는지)
meta (스키마 버전, 점검 주기, 마지막 정기 점검 시각)
```

| 표 | 주요 열 |
|---|---|
| `documents` | `doc_id`, `short`(인용 이름, 고유), `title`, `file_name`, `file_sha256`(중복 방지), `layer`, `kind`(guide/school/manual/reference), `school_id`, `publisher`, `published_year`, `is_base`, `status`(active/inactive), `toc_json`·`page_offset`(매뉴얼 목차), `summary`, `added_at`·`added_by`, `last_reviewed_at`, `next_review_due` |
| `doc_topics` | `doc_id`, `topic` |
| `doc_qtypes` | `doc_id`, `qtype` |
| `chunks` | `chunk_id`, `doc_id`, `page`, `section`, `text`, `tokens_json`, `embedding`(float32 BLOB), `embed_model` |
| `reviews` | `doc_id`, `reviewed_at`, `kind`(intake/periodic/manual), `verdict`, `weighted_score`, `report_json`(평가 전체) |
| `alerts` | `doc_id`, `review_id`, `severity`(critical/warn/info), `title`, `message`, `acknowledged_at`·`acknowledged_by` |

모든 하위 표는 `documents`에 `ON DELETE CASCADE`로 묶여 있어, 문서를 지우면 청크·주제·평가 기록·알림이 한 번에 지워집니다.

## 5. 자료의 생애(사용자가 넣고 빼는 흐름)

| 단계 | 화면 | 저장소에서 일어나는 일 |
|---|---|---|
| 추가 | 자료 관리 → 자료 추가 | 본문 비교로 같은 자료 차단(아래 중복·판 확인) → 평가 에이전트 판정 → 상담사 승인 → `documents`·주제·질문 유형 기록, 입고 평가(`reviews` intake), 주의할 점을 알림(info)으로 → 그 자료 청크만 임베딩해 `chunks`에 저장. 임베딩이 실패하면 등록 전체를 되돌림 |
| 중복·판 확인 | 자료 관리 → 자료 추가(업로드 직후) | `doc_agent/dedupe.py`: 파일 이름은 보지 않고 본문으로 비교. 숫자·연도를 지운 단어 4개 묶음 겹침(새 자료 중 겹침 / 등록 자료 중 겹침) + 표지 연도 vs 등록 발행 연도. 같은 자료(바이트 동일 또는 양쪽 85% 이상·같은 연도)면 평가 차단, 30% 이상 겹치면 개정판(연도 더 최근) / 구버전(더 오래됨). 실측: 가이드북 2025↔2026 82~88%, 정서행동 2025↔2026 26~54%, Wee 가이드 2024↔2025 48~63%, 관련 없는 자료 3% |
| 개정판 교체 | 자료 관리 → 자료 추가(개정판일 때, 삭제 동의 체크 필요) | `ingest.replace_edition`: 새 판 청크·임베딩을 먼저 만든 뒤 한 트랜잭션으로 교체. 자료 ID·인용 이름·질문 유형·평가 이력은 유지, 파일·제목·연도·청크 교체, 이전 판 목차 구간표 삭제, 이전 판 열린 알림 확인 처리 + "개정판으로 교체됨" 알림. 커밋 후 이전 판 PDF(data/·inbox/) 삭제. 기본 자료도 가능. 다른 선택: 이전 판 사용 중지 후 새 자료로 추가 / 둘 다 유지 |
| 사용 중지 | 자료 관리 → 등록 자료 | `status=inactive`. 청크는 남기고 검색에서만 뺌. 기본 자료도 가능, 되돌리기 가능 |
| 완전 삭제 | 자료 관리 → 등록 자료(확인 체크 필요) | 문서 행 삭제(청크·평가 기록·알림 CASCADE) + `data/`·`doc_agent/inbox/`의 PDF 삭제. 기본 4개 자료는 인용 이름을 직접 입력해야 삭제되고, 삭제하면 그 자리가 비어 질문 유형별 확인 순서·답변 규칙에서 빠짐 |
| 빈 기본 자리로 등록 | 자료 관리 → 자료 추가(비어 있는 기본 자리가 있을 때) | `add_document(base_slot=…)`: 지운 기본 자료의 ID·인용 이름(예: guide·가이드북)으로 등록 → 확인 순서·양식 연결이 되살아남. 원래 판 파일이면 목차·장 구간표도 그대로. 제목이 비슷한 자리를 기본 선택 |
| 다시 평가 | 자료 관리 → 등록 자료 | 평가 에이전트로 재평가 → `reviews`(periodic) + 알림 |
| 정기 점검 | 자동(학기마다) / 알림·정기 점검 탭 | 아래 6장 |
| 다시 만들기 | `build_index.py [--all | doc_id]` | PDF를 같은 이름으로 바꿨거나 청크 규칙을 바꿨을 때 그 자료 청크를 다시 만듦 |

## 6. 학기별 정기 점검과 사용 전 알림

- 주기: 182일(`meta.review_interval_days`). 마지막 점검 시각은 `meta.last_periodic_review`
- 자동 실행:
  - 앱을 열 때 점검 시기가 지났으면 백그라운드로 한 번 시작(`doc_agent/periodic_review.start_background_if_due`)
  - 앱을 열지 않아도 돌리려면 `run_review.bat`을 Windows 작업 스케줄러에 등록(README 참고). 시기가 아니면 바로 끝남
- 자료마다: 평가 에이전트로 다시 평가(오늘 날짜 기준 최신성, 자기 자신은 중복 비교에서 제외) → 직전 평가와 비교해 알림 생성

| 알림 | 조건 |
|---|---|
| 🔴 critical | 판정이 비추천(필수 기준 미달 등), PDF 파일 없음 |
| 🟠 warn | 판정 하락, 새로 0점이 된 기준, 최신성 점수 하락, 법·절차·학교 규정 자료가 발행 3년 경과, 학교폭력 자료인데 등록된 학교폭력예방법 시행일이 자료 발행 연도 이후(개정 조문 확인 필요), 점검 실패 |
| 🔵 info | 이번 평가의 주의할 점(이미 열린 같은 알림은 다시 만들지 않음) |

- 사용 전 알림이 보이는 곳
  - 챗봇 사이드바: "🔔 자료 유의사항 N건(긴급·주의) · 다음 정기 점검일"
  - 답변 바로 아래: 답변이 인용한 자료에 확인하지 않은 주의·긴급 알림이 있으면 "사용 전 확인" 상자
  - 자료 관리 → 알림·정기 점검: 알림 목록과 "확인함" 처리, 지금 점검 실행

## 7. 앞으로 확장할 때

- 여러 학교: `schools`에 학교를 추가하고 학교 자료의 `school_id`로 거른다(화면에서 학교 선택). 지금은 이산중 하나
- 여러 사용자·서버 배포: 같은 표 구조를 PostgreSQL + pgvector로 옮기고, `chunks.embedding`을 `vector(3072)` 열로 바꾼다
- 법령 원문(`data/학교폭력예방 및 대책에 관한 법률.jsonl`)을 `common` 층 자료로 넣으면 조문 단위 근거와 개정 비교를 더 정확히 할 수 있다(지금은 정기 점검의 시행일 비교에만 씀)
